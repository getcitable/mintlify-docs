Returns the one brand this call is authorized for: the brand an API key or single-brand connection is locked to, or, on an agency connection, the client brand the call named.

## When to use

- You need to verify which brand the key resolved to before acting (e.g. an autonomous agent's preflight check).
- `get_brand_context` returned something unexpected (wrong plan tier, wrong workspace) and you want the authoritative id and slug.

To operate on a different brand, create an API key under that brand in Citable (Settings → API keys), update the MCP config with it, and reconnect. Keys never grant access beyond their minted brand.

## Read-only behavior

Read-only. Does not change the active brand — the auth context is fixed for the session at connection time. To actually retarget writes to a different brand, update your MCP config (`CITABLE_BRAND_ID` env var for stdio, or regenerate the API key under the target brand for HTTP) and reconnect.

## Response

```
{ brands: [{ id, name, slug, planTier, planName, role, websiteUrl }], activeBrandId }
```

`activeBrandId` echoes the brand currently resolved by the auth context, so the caller can spot the active row.

Takes no arguments — user resolved from the auth context.
