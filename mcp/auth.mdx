---
title: Authentication and access
description: How a connection to Citable's MCP server is scoped to brands and an access level, and how to turn it off.
---

Every connection to Citable's MCP server is tied to one person and to the brands that person chose. The person is recorded on every action. Brand and person always come from the connection itself, never from a tool's inputs.

## Two ways to connect

**Sign in (OAuth).** For assistants that support it, such as Claude and ChatGPT. You sign in to Citable, choose the brands to connect and an access level. You can choose one brand or several, as long as you're a member of each.

**API key.** For assistants and scripts that don't support OAuth. Create a key in Citable under **Citable MCP › API keys** and send it as:

```
Authorization: Bearer <api_key>
```

A key belongs to the person who created it and to one brand.

## Access levels

The same three levels apply to sign-ins and API keys.

| Level | What it allows | Scopes |
| - | - | - |
| Read only | Every read tool: visibility, questions, content, attribution. | `read` |
| Drafts for my approval | Read only, plus creating drafts and proposals in Citable. Nothing goes live until a person approves it in Citable. | `read`, `draft` |
| Read, write and spend | Everything above, plus actions such as publishing, scheduling and managing ads. | `read`, `write` |

Calling a tool above the connection's level returns **403 `Insufficient scope`**, naming the tool and the scope it needs. The check runs before the tool does anything, so nothing is written.

A Drafts for my approval connection can make 50 draft or proposal calls a day. After that, those calls return **429 `Daily limit reached`** until midnight UTC.

**Read, write and spend works only on platforms we have reviewed.** A sign-in from any other app is limited to Drafts for my approval, whatever was selected. API keys are not affected by this limit, because a person creates each one deliberately.

A connection can never do more than the person behind it. Write access needs the member, admin or owner role on the brand, and it's checked on every call, so access drops as soon as that person's role does.

Give an assistant the lowest level that does its job. An assistant that only reports doesn't need to draft, and one that drafts doesn't need to publish or spend.

## Brand scoping

A connection works only with the brands it was given. Brand and person come from the connection, never from a tool's inputs.

## Turning a connection off

- **Sign-ins:** owners and admins see every app connected to a brand under **Citable MCP › Connected apps**, and members see their own. Choose **Disconnect**. The app loses access within 30 seconds.
- **API keys:** choose **Revoke** under **Citable MCP › API keys**. A revoked key fails immediately.
- **Either kind** stops working when its person is removed from the brand or the brand is deleted.
- **Resetting your password** turns off every API key and connected app made before the reset. Reconnect anything you still use.

API keys are shown once, when created. Treat them like any other secret. To rotate one, create a new key, update your integration, then revoke the old key.

## Rate limits

60 requests per minute, reads and writes together, counted per API key or per sign-in connection. Every response carries:

```
RateLimit-Limit: 60
RateLimit-Policy: 60;w=60
RateLimit-Remaining: 47
RateLimit-Reset: 42
```

`RateLimit-Reset` is seconds until the window resets. Over the limit, calls return a `Rate limit exceeded` error. Rate limits protect throughput; use access levels to control what a connection can do.
